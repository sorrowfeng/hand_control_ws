# 项目维护笔记

本文件记录 README 与《ROS2 工程说明》之外的工程知识：架构现状、SDK
接口覆盖情况、本机开发环境，以及实际踩过的坑。面向后续维护者，不是用户手册。

> 数据的时效性：SDK 覆盖统计、包数量等为 2026-09 的核对结果，改动后请更新。

## 代码结构与关键设计

- 接口规模：`hand_control_interfaces` 含 49 个 `.srv` + 3 个 `.msg`
  （`HandJointState`、`TactileState`、`TactileSite`），是其余包的公共依赖。
- `hand_control_service` 是唯一的 C++ 节点，源码分层为
  `BusBase` → `CanfdBus / Rs485Bus / EthercatBus`，`HandDevice`，
  `HandControlService::Impl`（pimpl）。主文件 `hand_control_service.cpp`
  约 1700 行，另有 CANFD / RS485 / EtherCAT（SOEM）三套 Master 后端。
- `hand_control_description` 是 Python 包，`models/` 下有多套手模型
  （两条产品线，左右手各一），每套自带 urdf/mjcf/meshes/config，可独立
  构建，具体目录名见该包 `models/`。`config/model.yaml` 的
  `active_model` 切换模型，`display.launch.py` 用 `OpaqueFunction` 解析。
- 服务/话题名都由 `serviceName(prefix, name)` 生成，prefix 即 `hand_names`
  中的手名。`compat_single_hand_services: true` 时会额外为默认手注册一份
  无前缀旧名，因此单手场景下同名服务存在两份
  （`/hand_control/<name>` 与 `/hand_control/hand/<name>`）。触觉话题
  **不生成**兼容副本，只有带手名的那一份。
- 实时状态固定走 topic（默认 100 Hz），模型侧不做服务轮询。
  `hand_state_publisher` 负责 deg→rad，并把主动关节映射到 URDF 关节树上
  （含 `joint_relations` 声明的从动关节）。
- SDK 差异只用 `cmake/sdk_adapter.hpp.in` 生成的头文件和
  `HC_SDK_NS` / `HC_SDK_CLASS` 两个宏隔离，不逐项包宏。第三方 SDK 位于
  `src/hand_control_service/thirdparty`，原则上不改其源码。

## SDK 接口覆盖现状（2026-09 核对）

核对方法：提取 `thirdparty/include` 下 SDK 头文件的公开方法，与
`hand_control_service.cpp` 中 `sdk()->` / `sdk_->` 的实际调用集合求差。

- SDK 公开接口 105 个，已覆盖 55 个。
- 两套厂商 SDK 头文件的公开接口完全一致（各 105 个，差集为空），
  切换 SDK 只需改命名空间与类名。

> 文档中统一用「SDK」「厂商」这类通用说法，不写具体厂商与库名：
> 分发打包的 forbidden 扫描会按厂商检查这些字符串。

未覆盖部分按优先级：

1. **触觉传感器**：`set_sensor_enable` / `set_finger_pressure_reset` /
   `get_finger_sensor_pos` 已开放，其余读数走 `tactile_state` topic。
   位点枚举 `LSS_*` 共 11 个（5 指尖 + 5 指腹 + 手掌）。
2. **手型与标定**：`get_hand_type`、`set|get_hand_direction`、
   `get_limit_target_angle`、`set|get_angle_conversion_enable` 等尚未开放，
   `hand_direction` 在 `service.yaml` 里还没有参数位。
3. `sync_position_to_target`（同步当前位置到目标）。
4. EtherCAT 的 SDO 驱动参数、OTA 升级、日志类接口：价值或优先级较低，
   宜独立实现。

**不是缺口，勿重复实现**：

- `set_velocity` / `get_velocity` / `get_now_velocity` 是
  `*_angular_velocity` 的旧别名，SDK 注释已注明默认等价。
- `get_pre_send_*` 属于「外部驱动总线」集成模式，与当前使用的
  `set_send_*_callback_ex` 回调模式互斥，二选一。
- `set_*_callback`（非 `_ex`）是老式函数指针版本。

真·功能空白：经典 CAN（非 CANFD）未支持。

### 触觉 SDK 语义要点

- 非 `_ex` 接口返回单点聚合标量；`_ex` 接口返回逐传感单元数组，且必须
  **两阶段调用**：先传 `nullptr` 取 `io_count`，再传 buffer 取数据。
  `io_count` 应按位点缓存（重连时失效重查），否则每帧调用次数翻倍。
- **头文件注释不可信**：`normal_force` / `tangential_force` 实际单位是
  牛顿 N（注释写 [0,1]）；`pressure` 与 `proximity` 才是归一化 [0,1]；
  `force_direction` 单位 deg。凡涉及量纲以实测或用户确认为准。
- `get_finger_pressure` 返回的是**相对零点基准的差值**，不先
  `set_finger_pressure_reset()` 读到的不是绝对压力。
- 采集固定遍历全部 11 个位点 × 5 通道，不做通道裁剪配置。

## 从代码反推的接口规范

新增服务时必须遵守，否则与既有接口风格不一致：

- getter 类 srv **不带** `int32 result`；失败时把输出置零/置空并打日志。
- setter 类 srv **带** `int32 result`。
- 服务名与 SDK 函数名保持 snake_case 同名，减少查文档成本。

## 本机开发环境

Windows 侧没有 ROS 2，**WSL2 是本机唯一可验证编译的途径**。

- 发行版 Ubuntu-22.04，`/opt/ros/humble`、`colcon` 已就绪。
- 工作区在 WSL 内的路径：`/mnt/d/Project/RosProject/hand_control_ws`。
- 调用方式：`wsl.exe -e bash -lc '<命令>'`。
- 全量构建约 5–6 分钟（interfaces 约 2m45s，service 约 2m40s），单包 2–3 分钟，
  命令超时建议给到 600000ms 以上。

在 WSL 里用 heredoc 写多行文件时 `\n` 会被字面传递，导致语法错误；
写多行内容改用：

```bash
printf "%s\n" "line1" "line2" "line3" > file
```

## 构建与调试踩坑

以下几条不易从报错看出来：

- **删除 `.msg` / `.srv` 后必须清理构建产物。** 增量构建不会清理
  `install/hand_control_interfaces` 里旧的 typesupport `.so`，它们仍引用
  已删符号，运行时报 `undefined symbol: ...__request__convert_from_py`，
  且失败点在 Python import 阶段，很难定位。保险做法是
  `rm -rf build/hand_control_interfaces install/hand_control_interfaces`，
  或直接全清。
- **C++ 里 `std::future::get()` 只能调用一次。** 写成
  `if (future.get()->result == 0) ... else ... future.get()->result`
  时，服务返回非 0 会抛 `std::future_error: No associated state`。
  必须先 `const auto response = future.get();`。Python 版
  `future.result()` 可重复调用，所以只有 C++ 示例会暴露。
- **没有 CAN 硬件时启动会持续重连。** 日志反复出现找不到通道 / 打开适配器
  失败之类的提示，属预期行为，不是代码问题；此时只能验证到「编译通过 +
  服务/话题正常注册」，采集链路要上真机才能确认。
- CANFD 后端默认是 gsusb-canfd（三平台通用），SocketCAN 与 libcanbus 为
  可选后端，切换开关与验证方法见 `README.md` 的「通讯方式 → CANFD」。
- 多行编辑代码后务必读回文件复核，避免误删相邻行。

## 厂商打包与 dist 规范

打包入口：`python scripts/package_vendor.py <vendor> --output-dir dist`，
厂商清单与裁剪规则在 `packaging/vendors.json`。

- 默认自动追加补零 ISO 日期子目录：`dist/2026-09-08/hand_control_ws_<vendor>.zip`。
  `--date YYYY-MM-DD` 指定日期（补打历史包用），`--no-date-subdir` 直接写进
  `--output-dir`（CI 固定路径场景用）。
- 同一天重复打包默认删除旧包，避免同日多版本混淆。
- **打包复制的是工作区当前文件，不是 git HEAD**，未提交的改动会直接进入产物；
  出包前先确认 `git status`。
- 排除项含 `build/ install/ dist/` 与 `.workbuddy/` 等本地数据，分发给厂商的
  包不应包含内部笔记。
- `dist/` 已被 `.gitignore` 忽略，不影响提交。历史目录存在非补零格式
  （如 `2026-7-2`），与新的补零格式并存；`verify_vendor_defaults/` 是验证用
  目录，保留原名。

## Git 与发布

- 仅 `main` 分支，推送 `origin/main`。
- **代理会破坏 GitHub 推送。** 本机配置了 `http.proxy=http://127.0.0.1:7890`
  （端口确实在监听），但经它推送会 TLS 握手失败：

  ```text
  fatal: unable to access 'https://github.com/...': TLS connect error:
  error:0A000126:SSL routines::unexpected eof while reading
  ```

  直连反而可用，单次绕过的写法：

  ```bash
  git -c http.proxy= -c https.proxy= -c http.postBuffer=524288000 push origin main
  ```

  首次直连可能报 `Recv failure: Connection was reset`，加大 `http.postBuffer`
  后重试即可，不必急着换网络。
- 诊断手段：`curl --noproxy '*' -o /dev/null -w "%{http_code}" https://github.com`
  测直连；`git ls-remote origin HEAD` 轻量验证连接，可快速区分「网络不通」与
  「push 传输问题」。
- 提交信息用中文，`feat: 主题` 加多段 `-m` 正文，正文按 功能 / 文档 / 工程
  分类罗列。
